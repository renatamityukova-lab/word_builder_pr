# Word Builder — «Наборщик»

Сервис для игры «Наборщик»: по исходному слову находит все слова, которые можно
составить из его букв **с учётом количества повторов**. Слова генерирует LLM,
а сервис проверяет каждый кандидат по буквам исходного слова, поэтому модель
используется только как генератор идей, а не как источник истины.

Доступны два интерфейса:

- **Gradio UI** — простая веб-форма «слово → список слов»;
- **FastAPI** — HTTP API с валидацией, кешем и корректными кодами ошибок.

---

## Возможности

- Валидация ввода до обращения к модели: одно слово, только буквы, 2–100 символов.
- Нормализация: обрезка пробелов и кавычек, нижний регистр, `ё` → `е`.
- Кеш результатов в памяти с TTL (по умолчанию 10 минут) — повторный запрос
  того же слова не обращается к LLM.
- Проверка кандидатов от LLM по «инвентарю» букв исходного слова
  (с учётом количества), удаление дублей и самого исходного слова.
- Сортировка результата: по убыванию длины, затем по алфавиту.
- Ретраи только для временных ошибок, автоматический переход на резервную модель.
- Типизированные ошибки и понятные HTTP-статусы (`400 / 502 / 503 / 500`).
- Структурированное логирование: консоль + JSON-файл с ротацией,
  единый `request_id` для всех сообщений одного запроса.
- API-ключ никогда не попадает в логи и тексты ошибок.

## Установка

Команды выполняются из **корня проекта** (каталог `word_builder`; он же корень
отдельного репозитория). Если проект лежит внутри общей рабочей папки,
сначала перейдите в него: `cd word_builder`.

```cmd
python -m venv .venv
.venv\Scripts\python.exe -m pip install -r requirements.txt
```

> В `requirements.txt` ветка `numpy` зафиксирована на `1.x`: на Windows/Python 3.11
> `numpy 2.x` падает с `ImportError: DLL load failed`, а Gradio тянет `numpy`
> транзитивно.

### Настройка окружения

Скопируйте шаблон и заполните ключ:

```cmd
copy .env.example .env
```

Минимально достаточно указать ключ и профиль:

```dotenv
APP_ENV=dev
OPENAI_API_KEY=your_api_key_here
```

`APP_ENV` выбирает профиль конфигурации: `dev` (по умолчанию) или `prod`.
Для эксплуатации задайте `APP_ENV=prod` — наложится `config/config.prod.yaml`
(адрес `0.0.0.0`, уровень `INFO`, без автоперезагрузки uvicorn).

Полный список переменных и параметров — в разделе
[«Конфигурация»](#конфигурация). Приоритет источников (сверху — важнее):
переменные окружения (`.env`) → `config/config.<APP_ENV>.yaml` →
`config/config.yaml` → значения по умолчанию.

Основной способ запуска — `uvicorn` из корня проекта. Вариант
`python api\server.py` работает так же: корень проекта попадает в путь импорта.

## Сценарий работы

1. **Валидация.** Слово проверяется до любых сетевых вызовов: должно быть
   строкой, одним словом, только из букв, длиной от 2 до 100 символов.
   Некорректный ввод не доходит до LLM.
2. **Нормализация.** Слово приводится к сравнимому виду: обрезка пробелов
   и кавычек, нижний регистр, `ё` → `е`.
3. **Кеш.** Проверяется общий кеш по нормализованному слову. При попадании
   LLM **не вызывается**, ответ помечается `from_cache: true`.
4. **Промпт.** Формируется запрос с исходным словом и инвентарём букв
   (`буква × количество`), минимальной длиной слова и лимитом количества слов.
5. **Вызов LLM.** OpenAI-совместимый `chat/completions`. Временные ошибки
   (таймаут, сеть, HTTP 429/5xx) повторяются до `max_retries + 1` попыток
   с экспоненциальной паузой; при недоступности основной модели используется
   `fallback_model`.
6. **Разбор и фильтрация.** Из ответа извлекаются слова (понимаются маркеры
   списка, запятые, кавычки, строки «слово — пояснение»). Каждое слово
   проверяется: только буквы, нужных букв не больше, чем есть в исходном слове,
   длина ≥ `min_word_length`, без дублей и без самого исходного слова.
   Результат сортируется по убыванию длины, затем по алфавиту, и ограничивается
   `max_results` словами.
7. **Кеширование.** Непустой результат сохраняется в кеш на `ttl_seconds`
   (по умолчанию 600 секунд). Пустой результат не кешируется.

Первый запрос к новому слову обычно занимает 15–30 секунд; повторный в течение
10 минут обслуживается из кеша почти мгновенно.

## API

### `POST /build`

Составить слова из букв исходного слова.

**Тело запроса** (`application/json`):

| Поле   | Тип    | Обязательное | Ограничения                            |
|--------|--------|--------------|----------------------------------------|
| `word` | string | да           | одно слово, только буквы, 2–100 символов |

Лишние поля не допускаются. Пробелы по краям обрезаются.

**Тело ответа** (200 OK):

| Поле         | Тип      | Описание                                   |
|--------------|----------|--------------------------------------------|
| `word`       | string   | исходное слово после нормализации          |
| `words`      | string[] | найденные слова (по убыванию длины)        |
| `total`      | integer  | количество найденных слов                  |
| `from_cache` | boolean  | `true`, если ответ получен из кеша         |

Во всех ответах API есть заголовок `X-Request-ID` — идентификатор запроса,
по которому можно найти все его записи в логе.

#### Пример: успешный запрос (curl)

```bash
curl -X POST http://127.0.0.1:8000/build \
  -H "Content-Type: application/json" \
  -d '{"word": "кот"}'
```

```json
{
  "word": "кот",
  "words": ["кто", "ток", "от", "то"],
  "total": 4,
  "from_cache": false
}
```

Повторный запрос того же слова в течение 10 минут:

```json
{
  "word": "кот",
  "words": ["кто", "ток", "от", "то"],
  "total": 4,
  "from_cache": true
}
```

#### Пример: клиент на Python

```python
import httpx

response = httpx.post(
    "http://127.0.0.1:8000/build",
    json={"word": "простокваша"},
    timeout=90,
)
response.raise_for_status()
data = response.json()
print(data["total"], data["from_cache"])
print("\n".join(data["words"]))
```

#### Пример: ошибка валидации — `400`

Запрос `{"word": "два слова"}`:

```json
{
  "detail": "Некорректный запрос — word: Нужно одно слово без пробелов.",
  "errors": [
    { "field": "word", "message": "Нужно одно слово без пробелов." }
  ]
}
```

Некорректный JSON в теле:

```json
{
  "detail": "Некорректный запрос — body: тело запроса должно быть корректным JSON",
  "errors": [
    { "field": "body", "message": "тело запроса должно быть корректным JSON" }
  ]
}
```

#### Пример: ошибка LLM — `502` / `503`

Модель вернула пустой или невалидный ответ (`502`):

```json
{ "detail": "Некорректный ответ модели: gpt-oss-120b: модель вернула пустой ответ" }
```

Модель недоступна после всех попыток и fallback (`503`):

```json
{ "detail": "Модель временно недоступна: Все модели недоступны — ..." }
```

Не задан ключ или доступ отклонён (`503`):

```json
{ "detail": "LLM не настроена: ..." }
```

Непредвиденная внутренняя ошибка (`500`) — без деталей:

```json
{ "detail": "Внутренняя ошибка сервиса" }
```

### `GET /health`

Проверка работоспособности.

```bash
curl http://127.0.0.1:8000/health
```

```json
{ "status": "ok" }
```

### Коды ответов

| Код | Когда возникает                                                                 |
|-----|---------------------------------------------------------------------------------|
| 200 | Успех (в том числе пустой список слов, если модель не предложила валидных слов)   |
| 400 | Некорректное тело запроса: пустое слово, несколько слов, цифры/знаки, > 100 символов, лишнее поле, невалидный JSON |
| 502 | Провайдер отклонил запрос (4xx, кроме 401/403/429) или модель вернула невалидный/пустой ответ |
| 503 | LLM не настроена (нет ключа, 401/403) или временно недоступна (таймаут, сеть, 429/5xx) после всех попыток и fallback |
| 500 | Непредвиденная внутренняя ошибка                                                 |

## Конфигурация

Слои конфигурации (сверху — важнее):

1. переменные окружения (`.env` или окружение процесса);
2. `config/config.<APP_ENV>.yaml` — профиль `dev` или `prod`;
3. `config/config.yaml` — общие значения;
4. значения по умолчанию в моделях `config/settings.py`.

| Профиль | Файл                      | Особенности                                                     |
|---------|---------------------------|-----------------------------------------------------------------|
| `dev`   | `config/config.dev.yaml`  | `127.0.0.1`, уровень `DEBUG`, автоперезагрузка uvicorn          |
| `prod`  | `config/config.prod.yaml` | `0.0.0.0`, уровень `INFO`, без консольных логов, TTL кеша 1 час |

Профиль задаётся переменной `APP_ENV` (по умолчанию `dev`). Неизвестное
значение приводит к ошибке при старте — защита от запуска prod с dev-настройками.
Секреты в YAML не хранятся: там указано только имя переменной с ключом
(`api_key_env`).

## Логирование

- Консоль — читаемый текстовый формат:
  `2026-01-01 12:00:00 | INFO | a1b2c3d4 | services.word_builder | ...`
- Файл — JSON, один объект на строку:
  ```json
  {"timestamp": "2026-01-01T12:00:00.000+00:00", "level": "INFO", "logger": "services.word_builder", "request_id": "a1b2c3d4", "message": "Кеш: попадание — 'кот', слов=4"}
  ```
- `request_id` связывает все сообщения одного запроса: UI-обработчик и API-middleware
  задают его, а записи из `services` и `llm` наследуют. В API он же возвращается
  в заголовке `X-Request-ID`.
- Логируются ключевые этапы: слово, попадание/промах кеша, формирование промпта,
  ответ модели, результат фильтрации и ошибки. Промпты и ответы целиком — на
  уровне `DEBUG`.

## Безопасность и публикация на GitHub

### Где хранится ключ

- **Только** в `.env` в корне проекта (локально) или в переменных окружения
  процесса (CI/CD, сервер, GitHub Secrets).
- YAML-профили хранят лишь имя переменной: `llm.api_key_env: OPENAI_API_KEY`.
- Код читает ключ через свойство [`LLMSettings.api_key`](config/settings.py) и
  использует его только в заголовке `Authorization`. Ключ не пишется в логи,
  тексты ошибок и ответы API.
- `.gitignore` исключает `.env`, `.env.*` (кроме `.env.example`), `logs/`,
  `__pycache__/`, `.venv/`, `.pytest_cache/`.
- Гигиену секретов проверяют тесты [`tests/test_secrets.py`](tests/test_secrets.py)
  и отдельная job `secrets` в CI: пайплайн падает, если `.env` попал в git
  или в отслеживаемых файлах найдена строка, похожая на ключ.

### Чек-лист перед публикацией

```cmd
:: 1. .env игнорируется (команда должна вывести правило .gitignore)
git check-ignore -v .env

:: 2. .env не отслеживается и не попадёт в коммит
git ls-files .env
git status --short

:: 3. ключа не было в истории
git log --all --oneline -- .env
```

- `git ls-files` и `git log` должны быть **пустыми**.
- Не загружайте проект на GitHub через веб-интерфейс «Add file → Upload files»:
  он **не учитывает `.gitignore`** и может загрузить `.env` вместе с остальными
  файлами. Используйте `git push` либо архив без `.env`, `logs/`, `.venv/`,
  `__pycache__/`, `.pytest_cache/`, `.ruff_cache/`.
- Для CI и деплоя задавайте ключ через **GitHub Secrets** и пробрасывайте его
  в переменную `OPENAI_API_KEY`; в репозитории секретов быть не должно.
- Публичный репозиторий = ключ скомпрометирован, если он там хоть раз появился.

### Если ключ всё-таки утёк

1. Немедленно **отозвать** ключ у провайдера и выпустить новый.
2. Убрать файл из индекса: `git rm --cached .env`.
3. Очистить историю (`git filter-repo` или BFG Repo-Cleaner) и выполнить
   force-push; уведомить всех, кто клонировал репозиторий.
4. Проверить логи и артефакты CI на наличие ключа.

Это standalone-версия для проекта как отдельного репозитория: все пути указаны
от корня проекта. В монорепозитории используется корневой
`.github/workflows/ci.yml` с фильтром `paths: word_builder/**`.

Пайплайн выполняет:

1. **secrets** — проверка, что `.env` не отслеживается и в файлах нет ключей;
2. **lint** — `ruff check .` (правила в `pyproject.toml`);
3. **tests** — установка `requirements.txt` и `pytest -q`;
4. **build** — `python -m compileall` и проверка загрузки профилей `dev` и `prod`.

Секреты в CI не нужны: `APP_ENV=dev`, ключ LLM читается только из окружения
и для тестов не требуется (HTTP-клиент подменяется в тестах).

---

## Тесты и линтер

Из корня проекта:

```cmd
.venv\Scripts\python.exe -m pytest
```

Проверка стиля и импортов:

```cmd
.venv\Scripts\python.exe -m ruff check .
```

Покрыты: успешный сценарий API, валидация и коды ошибок, кеш и его TTL,
клиент LLM (таймауты, ретраи, fallback), нормализация и фильтрация слов,
профили конфигурации `dev`/`prod`, приоритет источников настроек и гигиена
секретов (ключ не попадает в файлы, конфиги и дампы настроек).

Четыре обязательных сценария — успешный запрос, ошибка валидации, fallback при
сбое внешнего вызова и повторный запрос из кеша с логом `Кеш: попадание` —
подтверждены сквозными тестами ([`tests/test_integration.py`](tests/test_integration.py))
и fallback-тестами UI ([`tests/test_ui.py`](tests/test_ui.py)). Матрица
подтверждения и фактические результаты прогона — в
[`test_report.md`](test_report.md).

## Ограничения

- Кеш хранится в памяти процесса: при перезапуске сервиса он очищается,
  а при нескольких воркерах каждый имеет свой кеш. Бэкенды `file` и `redis`
  заявлены в конфигурации, но пока не реализованы (используется `memory`).
- Полнота и качество списка зависят от модели: сервис гарантирует только
  корректность слов относительно букв исходного слова, но не «словарную
  полноту». Каждое слово проверяется по буквам, поэтому «лишние» слова
  отбрасываются, а пропущенные моделью — не восстанавливаются.
- Сервис рассчитан на русскоязычные слова; промпт просит нарицательные
  существительные в именительном падеже единственного числа.
